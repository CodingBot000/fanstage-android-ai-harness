## 0. 사용자 지정 실행 지시

2026-11-16 사용자 지시에 따라 **채팅 책임 분리**와 **누락 데이터 처리·잔존 코드 정리**를 우선 처리한다. 기존 리뷰의 중요도 평가와 별개로 아래 실행 순서를 적용한다.

| 순서 | 작업 단위 | 포함 범위 | 제출·다음 행동 |
|---|---|---|---|
| 1 | 작업 A · 채팅 책임 분리 | 관련 R-00 검증 준비, R-03 연결 설정 처리 분리, R-04 메시지 정합성 저장소 추출 | 구현·검증 → 작업 A 커밋·푸시·PR 생성 → 해당 CI 확인 후 작업 B 진행 |
| 2 | 작업 B · 누락 데이터 처리와 잔존 코드 정리 | 관련 R-00 검증 준비, R-05 누락 아티스트 처리, R-06 미사용 코드·리소스·문서 정리 | 구현·검증 → 작업 B 커밋·푸시·PR 생성 → 해당 CI 확인 |
| 3 | 일시 정지·보고 | 작업 A·B의 결과와 남은 문제를 종합 | 후속 작업을 시작하지 않고 사용자에게 보고한 뒤 재개 지시 대기 |

**두 작업을 하나의 커밋이나 하나의 PR로 합치지 않는다.** R-03과 R-04는 작업 A의 내부 단계이며, R-05와 R-06은 작업 B의 내부 단계다. 내부 단계마다 추가 PR을 만드는 계획은 아니다.

R-01 오류 상태·복구 동작 변경과 R-02 초안 보존 변경은 이번 두 작업에 포함하지 않는다. 작업 A에서는 현재 동작을 테스트로 고정한 뒤 책임만 분리하며, 알려진 무동작 복구 버튼과 초안 유실은 후속 미완료 항목으로 기록한다. 이 두 문제를 해결하기 위해 우선 작업 범위를 확대하지 않는다.

누락 아티스트의 표시 방식 D-03은 2026-11-16 사용자 선택 A로 확정했다. 중립적인 대체 이미지와 알 수 없는 아티스트 이름으로 카드를 유지하며 영상 열기 동작을 보존한다. 정상 데이터의 이미지·이름은 그대로 사용한다.

문서 수정 이후 사용자가 **작업 진행**을 지시했다. 이에 따라 작업 A부터 구현·검증·Git 제출을 실제 수행하고 8절에 실행 결과를 기록한다. 두 작업이 완료되면 후속 작업은 일시 정지한다.

## 1. 목적과 완료 기준

현재 모듈 구조와 자원 소유권을 유지하면서 채팅 오류 상태, 미전송 초안, 채팅 내부 책임과 누락 데이터 처리를 정비한다. 각 작업은 동작 보정과 구조 변경을 구분해 작은 변경 단위로 검토한다.

이 문서는 실제로 확인한 문제, 정적 검토에서 찾은 위험, 구현 방법에 관한 제안을 구분한다. 문서 작성은 아래 구현이 완료됐거나 제품 정책이 확정됐다는 의미가 아니다.

다음은 후속 과제를 포함한 전체 리팩토링의 완료 조건이다. 이번 우선 작업 A·B의 완료·제출·일시 정지 기준은 8절을 적용한다. R-01·R-02가 남아 있다는 이유로 사용자 지정 범위를 확대하지 않는다.

- 오류 안내와 버튼이 실제 수행 가능한 동작에 대응한다.
- 초안은 확정된 보존·삭제 기준대로 동작하며, 화면·대화·게시물 사이에 섞이지 않는다.
- 채팅 순서·중복·누락·ACK·전송 결과 불확실성을 기존 계약대로 처리한다.
- 연결 설정 UI를 정리해도 Transport의 생성·인계·취소·해제 책임이 유지된다.
- 메시지 정합성 로직을 UI와 분리해 직접 테스트할 수 있다.
- 기존 테스트의 검증 범위를 유지하고, 변경된 동작의 회귀 테스트를 추가한다.
- 관련 빌드·Lint·단위·기기 검증 결과와 미실행 항목을 [검증 문서](../verification.md)에 기록한다.

### 3.1 R-01 · 누락 복구 버튼의 무동작

근거 코드: [ChatViewModel.kt](../../android/feature/live/src/main/kotlin/dev/fanstage/android/feature/live/chat/ChatViewModel.kt), [ChatContract.kt](../../android/feature/live/src/main/kotlin/dev/fanstage/android/feature/live/chat/ChatContract.kt), [ChatPanel.kt](../../android/feature/live/src/main/kotlin/dev/fanstage/android/feature/live/chat/ChatPanel.kt).

현재 흐름은 다음과 같다.

1. `accept()`는 잘못된 순번·길이, 충돌한 메시지, 미확정 전송과 맞지 않는 응답에 `invalidEvent = true`를 설정한다.
2. `publish()`는 실제 누락 여부와 `invalidEvent`를 합쳐 `gapUnresolved`로 내보낸다.
3. `ChatPanel`은 이 값이 참이면 누락 안내와 `retryGap()` 버튼을 표시한다.
4. `retryGap()`은 `highestObserved > cursor`일 때만 조회를 실행한다.

재현 조건은 정상 메시지의 `serverSequence = 1`을 받은 뒤 같은 순번에 다른 `messageId` 또는 본문을 보내는 것이다. 연속 확인 순번은 이미 해당 순번에 도달했으므로 복구 버튼을 눌러도 `fetchAfter()` 호출이 발생하지 않고 경고가 유지된다. 정상 메시지 보존 자체는 동작한다.

개선 방향은 누락 복구 상태와 프로토콜 문제를 독립적으로 표현하는 것이다. 충돌 표식을 무조건 지우거나 기존 확정·미확정 메시지를 초기화하는 방식은 채택하지 않는다. 충돌을 사용자에게 어떻게 설명하고 어떤 조치를 제공할지는 D-02를 따른다.

### 3.2 R-02 · 미전송 초안의 유실

근거 코드: [ConversationRoute.kt](../../android/feature/messages/src/main/kotlin/dev/fanstage/android/feature/messages/ConversationRoute.kt), [PostDetailRoute.kt](../../android/feature/community/src/main/kotlin/dev/fanstage/android/feature/community/PostDetailRoute.kt).

- DM 초안은 `remember(artistId)`, 댓글 초안은 `remember`로 보관한다.
- 각 입력창에 문장을 입력하고 `ActivityScenario.recreate()`를 실행하면 입력값이 빈 문자열로 바뀐다.
- 기존 `MessagesViewModel`·`CommunityViewModel`이 보유한 전송 완료 데이터와 미전송 입력의 수명은 다르다.
- LIVE 초안은 `ChatViewModel`의 메모리 상태에 있으며, 이 동작을 DM·댓글 정책의 승인 근거로 자동 확대하지 않는다.

개선에는 초안의 키, 소유자, 보존 범위, 전송 후 초기화, 화면 이탈 시 삭제를 함께 정의해야 한다. `rememberSaveable` 또는 `SavedStateHandle`로 일괄 교체하면 프로세스 복원 때의 보존 동작까지 달라질 수 있으므로 D-01 결정 전에 적용하지 않는다.

### 3.3 R-03·R-04 · 채팅 내부 책임의 집중

`ChatPanel`은 목록·설정·입력 UI 외에 실제 Transport 생성, 임시 연결 구독, 연결 확인, 취소와 인계를 수행한다. `ChatViewModel`은 화면 상태 외에 확정·미확정 메시지 저장, 중복·충돌 판정, 연속 순번, 누락 조회, 전송 Job과 메모리 임대를 함께 관리한다.

이는 구조 개선 제안이다. 현재 책임의 수만으로 Socket 누수나 성능 장애가 입증됐다고 해석하지 않는다. 기능 내부 객체를 추출하되 실제 수명은 기존 소유자에게 남긴다.

### 3.4 R-05 · 아티스트 누락 시 화면 예외

[MediaScreen.kt](../../android/feature/media/src/main/kotlin/dev/fanstage/android/feature/media/MediaScreen.kt)의 `LocalVideoCard`는 이미지 조회에서 `data.artists.first { it.id == video.artistId }`를 사용한다. 대응 항목이 없으면 예외를 발생시킨다. 같은 함수의 이름 조회는 `firstOrNull`을 사용하므로 누락 처리가 일관되지 않다.

현재 Fake 조합의 정상 재생 실패로 재현한 항목은 아니다. 빈 아티스트 목록과 누락 ID를 별도 fixture로 검증하고, D-03 결정에 따라 UI 상태를 매핑해야 한다.

## 4. 구현 전에 결정할 제품 동작

아래 표는 선택지와 권장 이유를 보존한다. 사용자 지정 작업 순서와 개별 커밋·푸시·PR·일시 정지 조건은 확정됐지만 D-01·D-02는 이번 우선 작업 이후로 보류한다. D-03은 사용자 선택 A로 확정했으며 같은 선택을 다시 확인하지 않는다. 조사·현재 동작의 테스트·동작을 바꾸지 않는 독립 추출 작업은 계속할 수 있다.

### D-01 · DM·댓글 초안의 수명 — 미정

| 선택지 | 동작과 영향 |
|---|---|
| A · 목적지 수명 동안 메모리 보관 · 권장 | 회전·Activity 재생성에서 유지하고 해당 BackStackEntry가 최종 제거되면 삭제한다. 프로세스 종료 후 복원하지 않는다. 기존 일반 ViewModel의 Activity 범위는 유지하고, 초안 전용 목적지 상태 소유자를 둔다 |
| B · 기존 Activity ViewModel에서 키별 보관 | 대화·게시물별 초안을 화면 재진입 때도 재사용하기 쉽다. Activity가 살아 있는 동안의 보존·명시적 삭제 시점과 저장 항목 상한을 추가로 정해야 한다 |
| C · OS 상태 복원 범위까지 보관 | `SavedStateHandle` 등으로 프로세스 재생성 후 복원을 지원한다. 입력 내용의 저장·복원·삭제 범위를 별도로 확정해야 한다 |

권장 A는 회전에 따른 입력 유실을 해결하면서 보존 범위를 화면 수명에 묶는다. 선택할 때 탭의 `saveState/restoreState`, 시스템 뒤로가기, 게시물 간 이동, 전송 성공·실패, 앱 종료를 각각 확인한다. 저장된 BackStack이 유지되는 경우와 최종 `pop`으로 제거되는 경우를 구분한다.

초안 식별자는 DM의 `artistId`, 댓글의 `postId`를 기본 후보로 한다. 계정 전환이 도입되면 계정 경계도 필요하지만, 계정 기능을 이번 리팩토링에 추가하지 않는다.

### D-02 · 충돌·잘못된 메시지의 안내와 복구 — 미정

| 선택지 | 동작과 영향 |
|---|---|
| A · 오류 유형별 안내, 실제 누락에만 복구 버튼 제공 · 권장 | 기존 확정 메시지와 미확정 전송을 유지한다. 충돌만 있을 때 무동작인 누락 버튼을 표시하지 않는다. 자동 초기화나 재동기화 절차를 새로 만들지 않는다 |
| B · 사용자가 재동기화를 실행할 수 있게 확장 | 충돌을 서버 조회로 다시 검증하는 상태·실패 안내가 필요하다. 기존 `cursor` 이전 충돌의 검증 방법, 미확정 전송 보존, 재조회 중 새 이벤트 합치기를 별도 계약으로 정해야 한다 |

상태 분리 자체와 복구 기능 확대는 분리한다. A를 선택하더라도 실제 누락과 충돌이 동시에 있으면 누락 복구는 수행할 수 있어야 하며, 복구 성공을 이유로 충돌 기록까지 사라지면 안 된다.

### D-03 · 아티스트가 누락된 로컬 영상 카드 — A 확정

2026-11-16 사용자가 **대체 이미지·이름으로 카드 유지**를 선택했다. 누락 아티스트는 중립적인 대체 artwork와 현지화한 이름으로 표시하고 영상 클릭은 유지한다. 아래 다른 선택지는 검토 이력이다.

| 선택지 | 동작과 영향 |
|---|---|
| A · 명시적 대체 표시로 카드 유지 · 권장 | 영상 접근을 유지한다. 대체 이미지·이름의 표현과 접근성 설명을 확정해야 한다 |
| B · 해당 카드 제외 | 유효한 아티스트가 있는 항목만 표시한다. 필터·빈 목록·영상 접근 가능성이 달라진다 |
| C · 불완전 데이터 상태로 안내 | 데이터 조합의 문제를 명확히 표시한다. 카드 단위와 목록 전체 중 어느 범위를 오류로 표시할지 정해야 한다 |

임의의 첫 번째 아티스트를 연결하면 잘못된 소속으로 표시될 수 있으므로 대체 매핑으로 사용하지 않는다. 아티스트가 있는 정상 카드의 동작과 외형은 유지한다.

## 5. 목표 책임과 상태 구조

아래 명칭은 신규 파일·타입의 후보이며 현재 코드에 존재한다는 의미가 아니다. 실제 추출 시 필요한 최소 표면적으로 확정한다.

### 5.1 화면·연결·메시지 책임

| 구성 요소 | 담당할 책임 | 소유하지 않을 책임 |
|---|---|---|
| `ChatPanel` 및 기능 내부 설정 Composable | 상태 표시, 목록 위치, 포커스·IME, 사용자 입력과 동작 전달 | 직접 네트워크 연결 생성·검증 |
| `LocalChatConnectionCoordinator` 후보 | 임시 연결 검증, 진행·오류 상태, 검증 취소, 인계 전 리소스 정리 | 룸의 활성 Transport, 메시지 이력, Player |
| `ChatTransportFactory` 또는 주입 가능한 생성 함수 | Fake·Real 생성 경로 제공, 테스트 대역 제공 | 연결의 영구 보유, 전역 가변 세션 |
| `ChatViewModel` | 룸 수명, `generation`, 수신·전송·복구 Coroutine, UI 상태 발행, 활성 Transport 종료 | Player, Compose 배치, 직접적인 JSON·HTTP 처리 |
| `ChatTimelineStore` 후보 | 확정·미확정 메시지와 순번, 중복·충돌 판정, 메모리 임대, 표시 snapshot | CoroutineScope, Socket, HTTP 호출, Android Context |
| `RealChatTransport`·`FakeChatTransport` | 현재 프로토콜과 전송·조회 계약 | UI 표시 정책과 초안 저장 |

초기 추출은 연결 처리와 메시지 저장소에 한정한다. 전송·복구 Job까지 각각 별도 계층으로 나누는 추가 추출은 실제 필요가 확인된 경우에 검토한다.

### 5.2 채팅 오류 상태

이 절은 **이번 두 작업에서 보류하는 R-01의 후속 설계 제안**이다. 작업 A에서는 현재 `ChatUiState`, `gapUnresolved`, `invalidEvent`의 외부 의미를 보존하며 아래 새 오류 상태·안내·복구 동작을 함께 도입하지 않는다.

후속 R-01에서 기존 `gapUnresolved`와 `invalidEvent`의 관계를 다음 개념으로 정리하는 안을 권장한다.

| 개념 | 표현 후보 | 갱신 책임 |
|---|---|---|
| 누락 조회 | `None`·`Recovering`·`Unresolved`의 `gapState` | 순번 상태와 복구 Job |
| 프로토콜 문제 | 잘못된 순번·길이, 충돌, 미확정 전송 불일치의 `protocolIssue` | 메시지 수락 판정 |
| 연결 상태 | 기존 `ChatConnectionStatus`와 인증·종료 오류 | Transport와 ViewModel |
| 전송 상태 | 기존 `Delivery`·`isUncertain`·전송 차단 | 전송 결과와 서버 확인 |

누락과 충돌은 동시에 존재할 수 있다. 둘을 상호 배타적인 단일 enum으로 합치지 않는다. 기존 필드의 호환이 필요하면 새 상태에서 계산하고, 같은 의미를 여러 가변 필드로 따로 갱신하지 않는다. 원본 메시지·토큰을 진단 문자열에 넣지 않는다.

### 5.3 연결 검증의 수명과 인계

연결 검증은 현재 `rememberCoroutineScope`에 묶여 있다. 책임 추출만으로 이를 장수하는 ViewModel 작업으로 바꾸면 Activity 재생성·화면 이탈 시 동작이 달라지므로 현재 취소 범위를 유지한다.

| 시점 | 소유자·해제 책임 |
|---|---|
| 검증용 `probe` 생성~종료 | 연결 담당 객체가 보유하고 성공·실패·취소에서 모두 종료 |
| 검증 Coroutine 취소·화면 dispose | 구독·HTTP를 취소하고 늦은 성공으로 현재 연결을 교체하지 않음 |
| 인계할 `next` 생성 후 `replaceTransport()` 호출 전 | 생성 측이 예외·취소 시 정리 |
| `replaceTransport(next)` 수락 | `ChatViewModel`이 활성 연결을 소유하고 기존 연결을 종료 |
| `replaceTransport(next)` 거절 | 현재 구현대로 해당 함수가 미사용 `next`를 종료. 생성 측이 중복 종료하지 않도록 인계 계약을 명확히 함 |
| Fake 전환 | 진행 중 검증을 취소. 미확정 전송이 있으면 기존 전환 차단을 유지 |

검증은 현재 `CONNECTED` 관측을 사용하며 전체 snapshot 완료를 보장하는 절차는 아니다. 책임 분리 단계에서 성공 판정 조건이나 타임아웃을 임의로 강화·변경하지 않는다. 필요하면 별도 기능 계약으로 다룬다.

endpoint와 설정 펼침 상태의 기존 복원, 토큰의 메모리 보관, 수락 후 토큰 초기화를 유지한다. 토큰을 `rememberSaveable`, `SavedStateHandle`, 저장 로그에 이동하지 않는다.

### 5.4 메시지 저장소 추출 시 보존할 규칙

- `confirmed`, `pending`, `uncertainIds`, `cursor`, `highestObserved`의 의미를 보존한다.
- 수락 결과를 신규 수락·동일 중복·프로토콜 거절 등으로 명확히 반환하고, ViewModel이 필요한 복구와 UI 갱신을 결정한다.
- 확정 응답은 해당 미확정 항목과 같은 키로 합쳐 화면 항목이 중복되지 않게 한다.
- 오래된 ACK가 이미 제거된 서버 행에 대응하더라도 보존 중인 미확정 전송을 올바르게 확정한다.
- 임대 키는 룸과 메시지 식별자의 기존 조합을 유지한다. 단순 객체 수를 논리 메시지 수로 대신하지 않는다.
- 여러 룸이 `ProcessChatMemory.budget`을 공유하는 현 구조와 미확정 항목 보호를 유지한다.
- `ChatMemoryBudget.acquire()`의 동기 eviction 콜백과 다른 소유자의 snapshot 갱신을 고려한다. 임대 해제·역참조·재진입으로 누락 또는 이중 해제가 발생하지 않아야 한다.
- 주 스레드에서 직렬로 상태를 변경하는 현재 전제를 유지한다. 저장소 추출을 이유로 백그라운드 동시 갱신을 도입하지 않는다.
- `generation`, `ensureActive()`, Job 취소와 Transport 종료는 ViewModel 경계에 남긴다.

성능 개선은 이번 추출의 검증된 결과로 주장하지 않는다. 자료구조나 이벤트 발행 주기를 바꾸려면 동일 조건의 별도 측정이 필요하다.

**완료 기준:** 재현 조건과 목표 계약이 구분되며, 초기 실패가 검증 기록에서 사라지지 않는다. 제품 assertion을 완화하거나 테스트를 비활성화하지 않는다.

### R-01 · 오류 상태와 복구 동작 정리

**이번 실행:** 보류. 작업 A·B 완료 후 일시 정지하며, 사용자 재개 지시 없이 이 단계에 착수하지 않는다.

**완료 기준:** UI 상태와 버튼 효과가 일치하고 기존 ACK·역순·누락 테스트가 통과한다. 이 단계에서 메시지 저장소 추출을 함께 수행하지 않는다.

### R-02 · 초안 상태 소유권 정리

**이번 실행:** 보류. 작업 A·B 완료 후 일시 정지하며, 사용자 재개 지시 없이 이 단계에 착수하지 않는다.

**진입 조건:** D-01 결정. **후보 범위:** `feature:messages`, `feature:community`, 필요한 `app` 목적지 조립과 계측.

1. 결정한 보존 범위를 기능 계약으로 기록한다.
2. DM은 `artistId`, 댓글은 `postId`를 기준으로 초안을 분리한다.
3. 초안 전용 소유자를 도입하는 경우 기존 일반 ViewModel 네 개의 Activity 범위는 바꾸지 않는다.
4. Route는 상태를 읽어 Screen에 표시하고 입력·전송 동작을 전달한다.
5. 전송 후 초기화와 실패 시 보존을 확정된 계약대로 처리한다. 현재 동기 Repository 호출에 임의의 네트워크 성공 의미를 부여하지 않는다.
6. 뒤로가기·탭 저장·재진입·다른 대상 이동·프로세스 재생성의 결과를 각각 검증한다.

**필수 사례:** DM·댓글 각각의 회전과 Activity 재생성, 서로 다른 대상의 초안 분리, 전송 후 초기화, 빈 입력, 목적지 제거와 재진입, 결정한 프로세스 종료 동작.

**완료 기준:** 확정된 보존·삭제 기준과 테스트가 일치한다. 초안이 화면 간 섞이거나 승인하지 않은 저장 범위로 확대되지 않는다.

### R-03 · 연결 설정 처리 분리

**이번 실행:** 작업 A의 첫 구현 단계. **진입 조건:** 현재 연결·취소 계약의 테스트 준비. R-01·R-02 완료는 필요하지 않다. **후보 범위:** `feature:live/chat`, 관련 Compose·통합 테스트.

1. 설정 영역을 기능 내부 Composable로 추출하고 표시 값·상태·이벤트를 명시적으로 전달한다.
2. Real 생성 경로를 주입 가능한 생성 함수 또는 Factory로 제공한다. 기존 Hilt 룸 생성 경로와 테스트용 Factory를 유지한다.
3. 임시 구독·연결 확인·취소·해제를 연결 담당 객체로 옮긴다.
4. 검증과 활성 연결의 소유권 인계를 테스트한다.
5. 포커스·키보드·설정 펼침·오류·Fake/Real 선택 표시·토큰 초기화와 기존 태그를 유지한다.

**필수 사례:** 올바른 연결, 인증 실패, 잘못된 URL·빈 자격 정보, 시간 초과, Fake로 전환 중 취소, 화면 이탈·재생성, 이전 검증의 늦은 완료, 미확정 전송으로 인계 거절, probe와 next의 정확한 종료 책임.

**완료 기준:** UI에서 직접 연결 검증 절차를 조립하지 않고, 모든 종료 경로를 대역과 실제 연결 양쪽에서 확인한다. Player 수명과 재생 상태는 영향을 받지 않는다.

### R-04 · 메시지 정합성 저장소 추출

**이번 실행:** 작업 A의 두 번째 구현 단계. **진입 조건:** R-03과 현재 메시지·오류 동작을 확인하는 회귀 기준 준비. **후보 범위:** `feature:live/chat` 및 관련 단위·계측 테스트.

사용자 지정 순서에 따라 기존의 R-01 선행 조건을 해제한다. 현재 동작을 보존하는 저장소 추출을 먼저 수행하고, 오류 상태 개편은 후속 R-01로 남긴다. 이후 R-01에서 저장소 API를 일부 조정할 수 있음을 기록한다.

1. 저장·수락·중복·충돌·순번·임대·표시 snapshot을 기능 내부 `ChatTimelineStore` 후보로 추출한다.
2. 전송·수신·복구 Coroutine과 `generation`은 ViewModel에 남긴다.
3. 기존 단위 테스트의 행동 검증을 유지하고 순수 저장소 규칙을 직접 검증한다.
4. [RoomNavigationSmokeTest](../../android/app/src/androidTest/kotlin/dev/fanstage/android/RoomNavigationSmokeTest.kt)의 `getDeclaredField("confirmed")` 의존을 해소한다.
5. 해당 계측의 Controlled Transport에 전용 `ChatMemoryBudget`을 주입하는 방법을 우선 검토한다. 자체 이력을 보관하지 않는 대역에서는 `budget.size`를 보관 수량 관찰에 사용하고, 종료 후 해제도 검사한다. 단위 테스트에서는 저장소 수량·복수 룸·Fake와의 공유 임대를 직접 검사한다.

**필수 사례:** ACK·echo 도착 순서, 동일 ID 재전송, 불확실한 전송, 확정 실패와 명시적 제거, 늦은 ACK, 페이지 경계 누락 복구, snapshot과 실시간 이벤트 교차, 보관·표시 상한, 모든 슬롯 보호 상태, 복수 룸 경쟁·종료, 여러 미완료 전송 취소.

**완료 기준:** 외부 동작이 작업 A 착수 시의 기준과 같고, 반사 접근을 제거해도 기존 보관 상한 검증을 대체 없이 삭제하지 않는다. 취소된 응답과 이전 룸 이벤트가 새 상태에 적용되지 않는다. R-03·R-04와 작업 A 검증을 마친 뒤 작업 A의 커밋·푸시·PR·CI 확인을 수행한다.

### R-05 · 누락 아티스트의 표시 처리

**이번 실행:** 작업 B에 포함. **진입 조건:** D-03 결정. **후보 범위:** `feature:media`와 관련 테스트. 모델 계약을 바꿀 경우 영향 범위를 먼저 재검토한다.

사용자가 확정한 D-03의 대체 표시·카드 유지 방식으로 구현한다.

1. 빈 아티스트 목록과 잘못된 `video.artistId`의 fixture를 만든다.
2. 이미지·이름 조회를 같은 누락 처리 규칙으로 매핑한다.
3. 선택한 대체·제외·오류 표시를 적용한다.
4. 정상 카드의 artwork, Center/TopCenter, Crop, 제목·설명, 클릭 대상, filter와 testTag를 유지한다.

**완료 기준:** 누락 fixture가 예외를 발생시키지 않고 결정한 화면 상태를 보인다. 정상 카드와 LIVE·VOD 경로 회귀가 통과한다.

### R-06 · 잔존 코드·리소스·문서 정리

**이번 실행:** 작업 B에 포함. **진입 조건:** 앞선 동작 변경과 독립된 참조 조사. R-01·R-02 완료는 필요하지 않다. **후보 범위:** 조사로 확인한 기능·공통 리소스·테스트·문서.

- `RoomListRoute`, `RoomListScreen`, `RoomListViewModel`, `RoomUiState`, `FakeRoomRepository`, `RoomRepository`의 제품·테스트·benchmark·스크립트 참조를 조사한다.
- 실제 런처는 `DiscoverRoute`를 사용한다. 남은 테스트 시나리오를 실제 사용 경로나 적절한 테스트 fixture로 옮길 수 있는지 먼저 판단하고, 동등한 검증이 확보된 항목만 정리한다.
- Lint의 미사용 리소스를 출발점으로 app/feature 간 중복 문자열을 확인한다. 동적 조회·계측·한국어 리소스와의 관계를 검사한 뒤 제거한다.
- 문서의 구현 전 분석, 구현 후 결과, 과거 CI·기기 실행 범위를 구분한다. 링크 검사 통과를 내용의 최신성 검증으로 대신하지 않는다.
- Gradle 공통 설정 정리와 라우트 타입 체계 변경은 별도 필요성이 확인될 때 다룬다. 이번 핵심 개선에 의존성·빌드 체계 변경을 묶지 않는다.

`app` 파일을 추가 분리할 경우 [모듈 검사](../../scripts/check-ux-module-boundaries.py)가 최상위 Kotlin 파일명을 고정 검사하는 점을 검토한다. 검사를 단순 삭제하지 않고 허용 조립 경계를 같은 수준으로 확인해야 한다. 현재 계획은 AppShell/NavHost의 추가 파일 분리를 선행 조건으로 삼지 않는다.

**완료 기준:** 참조가 끊기지 않고 회귀 범위가 유지된다. 실제 사용 중인 수동 Factory나 테스트 계약을 미사용으로 오인해 제거하지 않는다. R-05·R-06과 작업 B 검증을 마친 뒤 작업 B의 커밋·푸시·PR·CI 확인을 수행한다.

## 7. 검증 계획

검증 결과는 작업 A와 B를 구분해 남긴다. 내부 단계별 관련 검증 후 각 작업 전체의 빌드·Lint·단위·필요 계측·통합 검증을 확인하고 해당 작업의 커밋·푸시·PR로 제출한다. PR의 CI는 마지막으로 푸시한 head SHA를 기준으로 확인한다.

### 7.1 공통 명령

아래는 앞으로 구현할 단계의 검증 명령이다. 실행 예정이라는 이유로 PASS로 기록하지 않는다. JDK 17과 Android SDK 경로를 구성한 환경에서 실행한다.

저장소 루트:

```bash
python3 scripts/check-ux-module-boundaries.py
python3 scripts/check-portfolio-docs.py
git diff --check
```

`android/`:

```bash
./gradlew :app:assembleDebug :app:assembleRelease :app:lintDebug \
  testDebugUnitTest :core:data:test --no-daemon --max-workers=2

./gradlew :app:assembleDebugAndroidTest --no-daemon --max-workers=2
```

Hilt 바인딩·주입·ViewModel 생성에 영향을 주면 전용 소스셋을 컴파일하고 일반 소스셋도 다시 확인한다.

```bash
./gradlew :app:assembleDebugAndroidTest \
  -PfanstageHiltInstrumentation=true --no-daemon --max-workers=2
./gradlew :app:assembleDebugAndroidTest --no-daemon --max-workers=2
```

연결 기기가 여러 개면 명시적으로 선택하고 격리 테스트 패키지를 사용한다. 아래는 기존 테스트의 실행 예다. 기기 ID와 클래스는 해당 단계의 실제 대상에 맞게 바꾼다.

```bash
ANDROID_SERIAL=emulator-5554 ./gradlew :app:connectedDebugAndroidTest \
  -PfanstageDeviceTest=true \
  -Pandroid.testInstrumentationRunnerArguments.class=dev.fanstage.android.DeviceUiRegressionTest \
  --no-daemon --max-workers=2
```

| 변경 | 단위·정적 검증 | 기기·통합 검증 |

단계별 계측 후보에는 `UiContractTest`, `FloatingNavigationTest`, `CollapsingTitleBarTest`도 포함한다. 실제 변경 영향에 따라 선택하고 선택 이유를 기록한다. 실제 서버를 사용하는 테스트는 [서버 실행 안내](../../backend/chat-server/README.md)와 [장애 주입 계약](failure-recovery.md)에 따라 격리 환경에서 실행한다. Fake의 통과를 실제 서버 통합의 통과로 바꾸어 기록하지 않는다.

### 7.3 테스트 환경과 결과 해석

- 테스트명, 소스 SHA·미커밋 변경 여부, 빌드 변형, JDK, 기기/API, 키보드, 화면 설정과 명령을 함께 기록한다.
- `ActivityScenario.recreate()`는 Activity 복원 검증이며 실제 회전·프로세스 종료 검증과 구분한다.
- 키보드 초기 안내가 입력창을 가리는 경우 안내·IME 상태와 화면 근거를 확인한다. 제품 레이아웃 오류라고 단정하거나 검사를 느슨하게 하지 않는다.
- 재생 컨트롤의 최초 시간 초과는 후속 통과로 원인이 확정된 것이 아니다. 결정적인 시계 검증과 실제 재생 검증을 함께 유지한다.
- 일부 실패 사례의 재실행 통과를 전체 테스트 묶음의 단일 통과로 합산하지 않는다.
- 성능·누수·모든 기기 호환성은 별도 검증 범위다. 기존 감사의 미확정 상태도 새 근거 없이 변경하지 않는다.

## 8. 변경 단위, 진행 상태와 되돌리기

### 8.1 확정한 실행 순서

**작업 A의 관련 R-00 → R-03 → R-04 → A 커밋·푸시·PR·CI 확인 → 작업 B의 관련 R-00 및 D-03 결정 → R-05·R-06 → B 커밋·푸시·PR·CI 확인 → 일시 정지·종합 보고** 순서로 진행한다.

작업 A의 필수 검증이나 CI가 실패하면 원인을 해결하고 해당 작업 브랜치에 수정 커밋을 푸시해 다시 확인한다. 실패를 남긴 채 작업 A가 완료됐다고 표시하지 않는다. 작업 B는 확정된 D-03에 따라 누락 처리와 독립적인 잔존 코드 정리를 진행한다.

R-01·R-02와 기타 신규 개선은 이 실행 순서에 추가하지 않는다. 두 작업이 끝나면 사용자에게 보고하고 재개 지시를 기다린다.

### 8.2 작업별 커밋·푸시·PR 절차

1. **시작 상태 확인:** 현재 브랜치·기준 SHA·미커밋 변경을 확인한다. 이미 작성된 작업·현황·검증 문서를 보존하고 각 파일의 소속을 구분한다. 기존 사용자 변경을 초기화하거나 무관한 파일을 일괄 stage하지 않는다.
2. **작업 브랜치 분리:** 작업 A와 B에 각각 `codex/` 접두사 브랜치를 사용한다. 후보는 `codex/refactor-chat-responsibilities`, `codex/refactor-media-data-cleanup`이다. 실제 사용한 브랜치와 기준 SHA를 기록하고 두 작업의 제품 변경이 서로의 PR에 섞이지 않게 한다.
3. **구현·검증:** 해당 작업의 범위와 완료 기준을 충족한다. 검증 결과·실패 이력·남은 확인을 [검증 문서](../verification.md)에 기록하고 이 문서와 현황 문서의 진행 상태를 갱신한다.
4. **개별 커밋:** 각 작업에 대응하는 독립적인 커밋을 만든다. 예시 메시지는 A의 `refactor: separate chat responsibilities`, B의 `refactor: handle missing media data and remove unused code`다. 필요한 검증 보완은 같은 작업의 추가 커밋으로 남길 수 있으며 A와 B를 하나의 커밋으로 합치지 않는다.
5. **개별 푸시:** 해당 작업 브랜치를 원격에 푸시하고 로컬·원격 head SHA가 일치하는지 확인한다. `main` 직접 푸시나 이력 강제 재작성으로 제출을 대신하지 않는다.
6. **개별 PR 생성:** 작업 A·B에 각각 PR 하나를 생성한다. 문제와 결과 동작, 변경 범위, 검증 명령·환경·결과, 미실행 항목과 남은 문제를 한국어로 설명하고 관련 계약·검증 기록을 연결한다. 공유 계획 문서의 커밋 기반과 충돌은 분리 과정에서 보존·정리한다. 두 작업의 최종 공통 계획·현황·검증 보고는 양쪽 PR에서 같은 내용으로 맞추고, 그 보고 변경 이후 각 PR의 마지막 head CI도 다시 확인한다. 제품 변경의 작업별 분리는 유지한다.
7. **CI 확인:** 각 PR의 마지막 head SHA에서 필요한 검사가 실제 실행되어 통과했는지 확인하고 실행 링크를 기록한다. 현재 [통합 품질 게이트](../../.github/workflows/required-quality.yml)는 `main` 대상 PR에 동작하므로 두 PR의 제출·검증 기준도 `main` 대상으로 구성한다. 다른 base에서 CI가 생기지 않은 상태를 PASS로 간주하지 않는다.
8. **다음 작업 또는 정지:** A의 제출·확인을 마치면 B를 진행한다. B까지 완료하면 8.4절에 따라 일시 정지하고 보고한다.

이 제출 절차는 사용자 실행 지시에 따라 수행한다. 같은 정상 제출 절차를 매 단계마다 다시 승인받지 않는다. PR 생성과 CI 확인까지를 제출 완료 범위로 하며 PR 병합은 완료의 선행 조건이 아니다.

### 8.5 변경 단위와 되돌리기

작업 A와 B는 독립 리뷰와 되돌리기가 가능한 변경으로 유지한다. 동작 보정과 무관한 대규모 이름·파일 이동, 의존성 업그레이드를 함께 넣지 않는다.

되돌릴 때는 실제 의존 관계를 확인해 후속 변경부터 역순으로 revert하고 관련 검증을 다시 실행한다. 테스트 결과·원본 실패 기록을 삭제하거나 reset·force push로 이력을 재작성하지 않는다. 메시지·초안 데이터 삭제나 서버 저장소 초기화를 코드 롤백의 일부로 수행하지 않는다.
